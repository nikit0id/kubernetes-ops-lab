# k3s: три узла, ingress и сертификаты

Этап «Кластер» из [issue #3](https://github.com/nikit0id/kubernetes-ops-lab/issues/3). Стенд поднимается одной командой на локальном Docker и не пересекается с kind-стендом из основного README: отдельный Compose-проект `k3s-lab`, отдельный kubeconfig `.local/k3s/kubeconfig` и отдельный контекст `k3s-lab`.

## Что получится

| Компонент | Решение |
|---|---|
| Топология | Один server с embedded etcd (`--cluster-init`) и два agent |
| Ingress | ingress-nginx 4.15.1, встроенный Traefik отключён флагом `--disable=traefik` |
| Сертификаты | cert-manager v1.21.3, ClusterIssuer на собственном корневом CA |
| Проверка | Три Ready-узла, DNS CoreDNS, HTTPS через ingress и валидный сертификат |

## Требования

Docker Engine в режиме Linux-контейнеров, kubectl, Helm 3, Python 3.13+ и `openssl`. Все инструменты — в одной среде: не смешивайте Windows kubectl с kubeconfig из WSL.

## Bootstrap одной командой

```bash
python scripts/k3s_lab.py doctor
python scripts/k3s_lab.py up
```

`up` последовательно: проверяет инструменты, создаёт токен кластера один раз, выбирает свободные порты, собирает `ops-lab:1.0.0`, поднимает три контейнера, ждёт готовности API, ждёт три Ready-узла, импортирует образ во все узлы, ставит ingress-nginx и cert-manager, создаёт корневой CA и применяет манифесты из `k3s/manifests`.

Если Compose-проект `k3s-lab` уже существует, `up` намеренно откажется работать. Дальше — `verify`, а не повторный `up`.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `K3S_VERSION` | `v1.34.13-k3s1` | Тег образа `rancher/k3s`; тег `latest` не используется |
| `K3S_API_PORT` | 6443, иначе свободный | Публикация API на 127.0.0.1 |
| `K3S_HTTP_PORT` | 8081, иначе свободный | Публикация ingress :80 |
| `K3S_HTTPS_PORT` | 8443, иначе свободный | Публикация ingress :443 |

Фактически выбранные порты сохраняются в `.local/k3s/ports.json`.

## Проверка

```bash
python scripts/k3s_lab.py verify
```

`verify` не доверяет коду возврата `helm` и не считает применение манифеста доказательством. Он проверяет:

1. Ровно три узла и все три в состоянии `Ready`.
2. Наличие namespace `kube-system`, `ingress-nginx`, `cert-manager`, `smoke`.
3. Готовность подов CoreDNS.
4. `rollout status` для тестового Deployment.
5. Условие `Ready` у объекта `Certificate` — то есть сертификат действительно выпущен, а не просто запрошен.
6. Реальный HTTPS-запрос к `smoke.lab.localhost` через опубликованный порт с проверкой цепочки по локальному корневому CA.

Шаг 6 — единственное доказательство, что путь «ingress → Service → Pod» работает вместе с TLS. Остальные шаги проверяют компоненты по отдельности.

## Локальный DNS и сертификат

Домен `*.lab.localhost` разрешается в `127.0.0.1` самим браузером по правилам `.localhost`; записи в `hosts` не нужны. Корневой CA лежит в `.local/k3s/ca/tls.crt`. Чтобы браузер доверял сертификату, импортируйте этот файл в доверенные корневые центры **своей** машины — команда этого не делает и не меняет системные хранилища.

```bash
curl --cacert .local/k3s/ca/tls.crt https://smoke.lab.localhost:8443/healthz
```

Порт подставьте из `.local/k3s/ports.json`, если 8443 был занят.

## Ограничения

- Три узла на одной машине — не HA: все контейнеры делят один Docker daemon и один диск. Потеря узла здесь имитируется остановкой контейнера, а не отказом оборудования.
- Embedded etcd запущен в единственном экземпляре, поэтому кворума при потере server нет. Это осознанно: этап DR с бэкапом etcd — отдельный пункт плана.
- Образ загружается в узлы через `k3s ctr images import`, реестр не используется. Для этапа GitOps понадобится либо реестр, либо тот же приём.
- Traefik отключён намеренно: два ingress-контроллера на одних портах конфликтуют, а ingress-nginx выбран как основной.
- Сертификат самоподписанный. Для реального домена нужен ACME-Issuer и доступный извне `HTTP-01`/`DNS-01`.
- `K3S_KUBECONFIG_MODE=644` внутри контейнера нужен, чтобы файл прочитался с хоста; каталог `.local/` исключён из Git.

## Удаление

```bash
python scripts/k3s_lab.py down
```

Удаляет контейнеры и тома проекта `k3s-lab`. Kind-стенд, его образы и данные не затрагиваются. Для диагностики: `python scripts/k3s_lab.py logs`.
